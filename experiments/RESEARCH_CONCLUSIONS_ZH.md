# 实测结论与下一步

这次已经把持久化求解完整纳入单一 Seamwise 方法，并完成真实电路、相同噪声样本上的参考后端配对实验。24 个配置覆盖 block 数至 32、distance 至 11、深度至 14；168 个请求中 136 个完成完整测量协议，32 个未完成单列。37 组配对的 2,560 次 shot 执行没有纠错向量或已记录增长轨迹差异。另做了 18 次独立进程计时复测，复用输入不增加独立纠错样本数。

## 结论成立的部分

- 在主 surface-code 点和 BB144 高噪声点，三轮计时复测的配对平均延迟中位降幅分别为 8.0% 与 17.9%，输出保持一致。
- 八个固定 BB144 输入的单独诊断中，basis insertion 调用从 81,639 降到 3,100。这是重复列处理的计数，不是 word-operation 计数或端到端加速倍数。
- 相同输出的保证可以从单个 oracle 延伸到整个确定性初始化、fallback 与 repair 流程。所有 HUF 阶段的工作可以统一按累计访问列数计费；width-two、zero-halo、单次 radius-one 修复且最多一次全局 fallback 时，累计列访问上界为 3N_f。准备、离线 rank 与额外逻辑事件计算另外计费。
- 生成电路的局部提取、单层 CNOT matching 与记录重置结构，给出了有条件的 detector 稀疏性理由；这不等价于任意深 transversal 电路都保持稀疏。

## 数据不支持的部分

- 主实验完整 256 个样本中，BP 引导两种 HUF 后端都是 29 次失败；Tesseract 是 10 次。不能宣称纠错准确率全面领先。
- 主实验前 64 个输入的三轮复测中，Tesseract 也比当前持久化参考实现快。完整 256 输入单轮均值的排序不同，说明尾部困难样本与样本集选择会影响均值，不能挑一个均值当普遍优势。
- 两种 HUF 模式的整进程采样 RSS 在两个复测点没有明显下降，约为 112 MiB 和 138 MiB；不能把理论空间界包装成已经测出的明显省内存收益。
- 当前是新写的 Python 参考实现，使用全局 bitsets、minimum-label DSU、重复 pivot 排序与诊断状态。不是原作者 HUF 实现，也不是理论中 support-local/union-by-rank 的优化实现。基线共享状态容器与数据路径，结果属于受控 oracle 消融，不能替代优化原版 HUF 的复现。
- 2026 的 GARI、ghost 等专用方案尚未验证适配；Relay-BP 的原生依赖安装失败。不能把这些未运行项目列为已战胜的基线。
- 64 样本下的零失败不能支持低逻辑错误率或 threshold 结论。固定三轮提取的 distance 扫描也不是 threshold 实验。

## 优先级

1. 先把比较对象补齐：取得原版 HUF/可信原生实现，并完成 Relay-BP、2026 相关解码器与相同观测量、相同电路的接口验证。
2. 按 profiling 优化公共图管理成本：组件初始化、DSU root 查询、eligibility 扫描。代数复用已经减少大量重复插入，但剩余路径占了大部分开销。不要只继续优化 XOR。
3. 在全部规模点做共同资源预算、独立进程复测与准确率—延迟前沿；为稀有错误预先固定统计精度与采样预算。
4. 再检验逻辑 reach 证书是否能够指导更有效的修复带扩张。当前证书是可计算结构结论，不是已验证的准确率提升策略。

现阶段成立的研究定位是：具有精确输出保持保证和受控局部提速的边界修复框架。把它写成全面 SOTA，会与已测到的强基线结果直接矛盾。
